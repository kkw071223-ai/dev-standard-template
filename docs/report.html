NVIDIA가 공개한 Omniverse 에이전트·스킬 생태계를 전부 찾아내고, 샌드박스에서 직접 실행해 입력과 출력을 기록했습니다. 문서를 읽고 정리한 게 아니라, 실패한 명령까지 그대로 남긴 실행 기록입니다.

01

먼저, 용어 네 개만

이 분야는 약어가 많아서 처음엔 벽처럼 느껴집니다. 하지만 실제로 필요한 개념은 네 개뿐입니다.

USD
3D 씬의 파일 형식. 3D 업계의 PDF 같은 존재입니다. 원래 픽사가 만들었고, Omniverse 전체가 이걸 공통 언어로 씁니다. 텍스트(.usda)로 열어 읽을 수 있습니다.
SimReady
“시뮬레이션에 쓸 수 있는 상태”의 규격. 3D 모델이 예쁘게 보이는 것과, 물리 엔진에서 제대로 굴러가는 것은 전혀 다른 문제입니다. 마찰 계수가 없거나 충돌 형상이 없으면 보기엔 멀쩡해도 시뮬레이션은 엉망이 됩니다. SimReady는 그 조건들을 코드로 번호 붙여 정의한 표준입니다.
Skill (스킬)
에이전트에게 주는 작업 설명서. SKILL.md 파일 하나와 실행 스크립트들이 담긴 폴더입니다. Claude Code·Cursor 같은 도구에 설치하면 에이전트가 그 절차를 따라 일합니다.
MCP 서버
에이전트가 질문할 수 있는 지식 창구. “이 API 어떻게 쓰지?”에 답해줍니다. 중요한 점: 실행은 하지 않습니다. 아는 것과 하는 것이 분리돼 있습니다.
비유 USD는 도면, SimReady는 납품 검사 기준, 스킬은 작업 지시서, MCP는 기술 문의 창구입니다. 이 보고서의 핵심은 “납품 검사에서 떨어진 도면을 에이전트가 스스로 고쳐서 통과시킬 수 있는가”입니다.
02

ovstream은 영역이 다릅니다

질문 주신 부분입니다. 처음 조사에서 ovstream은 설치·임포트만 확인하고 깊이 파지 않았습니다. 이번에 API를 열어보니 확실히 다른 영역이었습니다.

NVIDIA 개발자 페이지 요약에는 “GPU 데이터 공유”라고 적혀 있어서 저장·전송 계층인가 했는데, 실제 패키지 내용은 GStreamer 기반 영상 스트리밍 + 원격 입력 라이브러리였습니다. 즉 렌더링 결과 화면을 사용자에게 보내고, 마우스·키보드를 되받는 계층입니다.

ovstream 실제 API — 직접 확인
$ python -c "import ovstream; print(ovstream.__doc__)"
OVSTREAM SDK Python bindings.
    ovstream.initialize()
    with ovstream.Server(ovstream.ServerType.RTSP) as server:
        server.start(ovstream.ServerConfig(width=1920, height=1080))

전송 방식 5종   ServerType: WEBRTC, NATIVE, RTSP, SHM, CUDASHM
입력 이벤트 4종 InputEventType: KEYBOARD, MOUSE, GAMEPAD, TOUCH
프레임 타입     VideoFrame, AudioFrame, CudaSync

$ python -c "import ovstream; ovstream.initialize()"
OSError: libcuda.so.1: cannot open shared object file
중요한 차이 ovphysx(물리)는 GPU가 없으면 CPU로 알아서 내려앉습니다. 그런데 ovstream은 초기화 자체가 실패합니다. NVENC 하드웨어 인코더에 의존하기 때문입니다. 제가 테스트한 Omniverse 라이브러리 중 CPU 폴백이 없는 유일한 경우였습니다.

그래서 어디에 쓰나

ovstream은 혼자 쓰는 게 아니라 세 개가 한 조입니다. ovrtx가 화면을 그리고 → ovstream이 그걸 내보내고 → ovui가 UI를 얹습니다. “브라우저에서 Omniverse 씬을 돌려보게 하고 싶다”가 목표일 때 쓰는 조합입니다. omniverse-realtime-viewer 스킬(하위 레퍼런스 54개)이 정확히 이 작업을 위한 것입니다.

지금 사용자님 목적(자산 준비 자동화)에는 필요하지 않습니다. 뷰어를 직접 만들 단계가 되면 그때 꺼내면 됩니다.

03

생태계 규모 — 40~50개가 아니라 147개

“40~50개 이상”으로 추정하셨는데, Omniverse 관련만 세어도 그보다 많습니다. 마케팅 페이지를 읽은 게 아니라 저장소를 클론해서 디렉터리를 센 숫자입니다.

구조를 알면 숫자가 이해됩니다. 최상위 스킬은 대부분 라우터라서, 그 안에 실제 작업 단위가 중첩돼 있습니다. 예를 들어 omniverse-cad-to-simready 하나가 15개 하위 레퍼런스와 23개 실행 스크립트를 품고 있습니다.

04

직접 돌린 것 — 로봇 하나를 끝까지

여기가 본론입니다. 관절 2개짜리 로봇 팔 URDF 파일 하나(1.6 KB)를 만들어서, NVIDIA 실제 도구 체인에 통과시켰습니다. 각 단계에서 무엇이 들어가고 무엇이 나왔는지 그림과 터미널 출력으로 남겼습니다.

  1. 1

    URDF → USD 변환

    URDF는 로봇 기술 표준 포맷입니다. 이걸 USD로 바꿉니다. 1.6 KB 텍스트가 6개 레이어로 이루어진 USD 자산이 됩니다.

    urdf_usd_converter
    $ urdf_usd_converter arm2.urdf out/arm2
# 2초 미만, 종료코드 0

out/arm2/arm2.usda                    ← 인터페이스 레이어
out/arm2/Payload/Contents.usda
out/arm2/Payload/Geometry.usda
out/arm2/Payload/Materials.usda
out/arm2/Payload/MaterialsLibrary.usdc
out/arm2/Payload/Physics.usda         ← 총 40 KB

    변환기가 알아서 결정한 것들이 있습니다. 관절 한계값이 라디안에서 도(degree)로 바뀌고(1.57 → 89.95), Newton 물리 엔진 스키마가 자동으로 붙고, URDF의 effort 값은 USD에 의미가 없지만 custom float urdf:limit:effort로 보존됩니다. 요청하지 않은 고정 관절도 하나 생깁니다.

  2. 2

    변환 결과를 눈으로 확인

    USD 파일 안의 좌표를 읽어서 그림으로 그렸습니다. 여기서 중요한 걸 알 수 있습니다 — 변환기는 각 링크마다 보이는 형상과 부딪히는 형상을 따로 만들고, purpose 속성으로 구분합니다.

    알아두면 좋은 것 충돌 형상이 purpose = guide로 표시된 덕분에, 나중에 “모든 렌더링 대상에 재질이 있어야 한다”는 규칙(VM.MAT.001)에서 자동으로 면제됩니다. 규격들이 서로 맞물려 설계돼 있습니다.
  3. 3

    USD 검증 — 통과. 그런데 SimReady 검증 — 실패

    먼저 일반 USD 검증기를 돌리면 깨끗하게 통과합니다. 그런데 SimReady 규격으로 검사하면 6개 항목에서 실패합니다. 이 간극이 이 보고서의 핵심입니다.

    두 검증기의 상반된 판정
    $ nvidia_usd_validate out/arm2/arm2.usda
No issues found.   종료코드 0

$ simready-validate out/arm2/arm2.usda --profile Prop-Robotics-Neutral
FAIL NP.005  다른 USD 파일이 폴더에 있으면 안 됨: Geometry.usda, Physics.usda, ...
FAIL RB.006  강체가 강체의 자식인데 xformstack reset이 없음  (×2)
FAIL GSP.001 파지 벡터 프림이 최소 1개 있어야 함
FAIL NP.006 SimReady 메타데이터가 없음
FAIL PMT.001 충돌 형상에 물리 재질이 연결되지 않음

  [FAILED] Prop-Robotics-Neutral v1.0.0   2/6 통과

    각 실패에 번호가 붙어 있는 것이 결정적입니다. “뭔가 이상하다”가 아니라 “RB.006 위반, 위치는 이 프림”이라고 나오기 때문에, 에이전트가 정확히 무엇을 고칠지 알 수 있습니다.

    NVIDIA 도구끼리 충돌 NP.005는 “자산 폴더에 USD 파일은 하나만”을 요구합니다. 그런데 방금 NVIDIA 자체 변환기가 만든 것은 6개 레이어짜리 구조입니다. 즉 NVIDIA의 규칙이 NVIDIA의 변환기 출력을 거부합니다. 둘 다 각자 옳지만 전제가 다르고, 누군가는 조정해야 합니다. 그 자리가 에이전트 자리입니다.
  4. 4

    자동 수정 → 6/6 통과

    6개 항목을 닫는 스크립트를 작성했습니다. 각 검사기의 소스 코드를 읽고 정확히 무엇을 요구하는지 확인한 뒤 구현했습니다 — SimReady 규격이 실행 가능한 파이썬이라서 추측할 필요가 없습니다.

    첫 시도는 실패했습니다 RB.006이 계속 남았습니다. 제 코드가 조상 중에 이미 수정된 것이 있으면 멈추도록 되어 있었는데, 검사기 소스를 읽어보니 각 프림이 자기 자신에 표시를 가져야 했습니다. 조상의 표시는 자손을 덮지 않습니다. 한 줄 고치고 통과했습니다.

    이건 단순한 형식 규칙이 아닙니다. URDF의 관절 트리가 USD에서 중첩된 강체가 되는데, 중첩 강체에 변환 스택 초기화가 없으면 시뮬레이션 결과가 정의되지 않습니다. 순진한 변환이 만드는 실제 물리 버그입니다.
  5. 5

    검사만 통과하고 물리가 깨졌으면 무의미하다

    규격을 맞추려고 자산을 수정했으니, 움직임이 망가지지 않았는지 반드시 확인해야 합니다. 실제로 물리 시뮬레이션을 돌리고 관절 각도를 초당 60회 기록했습니다.

    이 그래프가 증명하는 것 원본 URDF에 upper="1.57", upper="2.0"이라고 쓴 값이, USD로 변환되고(내부적으로는 도 단위로 바뀌고) PhysX 엔진에 올라가서까지 정확히 지켜졌습니다. URDF → USD → 물리 엔진 전체 체인이 온전하다는 눈에 보이는 증거입니다.

    어깨 관절(파랑)은 중력을 받아 7 rad/s까지 가속했다가 한계에서 멈추고, 손목 관절(빨강)은 중력 토크가 없어서 준 속도 그대로 갔다가 멈춥니다. 물리적으로 맞는 거동입니다.
  6. 6

    다른 포맷으로도 되나 — MuJoCo에서 새 문제 발견

    같은 파이프라인을 MuJoCo 형식(카트폴)에 돌렸습니다. 그러자 URDF에는 없던 새 실패 항목이 나왔습니다.

    대응은 3단계와 같았습니다. 검사기 소스를 읽고 (“purpose가 default거나 render인 모든 형상에 재질이 연결돼야 함”), 40줄쯤 추가하니 양쪽 다 6/6이 됐습니다.

    그런데 왜 한쪽만 실패했는지가 더 흥미롭습니다. 두 자산의 프림을 비교해보니 구조가 근본적으로 달랐습니다.

    arm2 (URDF)cartpole (MuJoCo)
    보이는 형상purpose=default, 충돌 없음 같은 프림이 둘 다 담당
    purpose=default + 충돌
    충돌 형상purpose=guide, 별도 프림
    VM.MAT.001 대상 시각 형상만 — <material>에서 재질 받음 충돌 겸용 형상까지 — 재질 없음 실패

    URDF 변환기는 시각과 충돌을 분리하고 충돌 쪽을 guide로 표시해서 재질 검사에서 면제시킵니다. MuJoCo 변환기는 하나의 형상이 둘 다 담당하게 만들기 때문에, 그 형상이 재질 검사 대상이 되어버립니다. 규격 위반이 아니라 변환 관례의 차이가 만든 결과입니다.

    여기서 배울 점 — 자동화가 복리로 쌓입니다 새 요구사항 코드 하나를 처리하는 데 검사기 한 번 읽기 + 40줄이 들었습니다. 그리고 그 코드는 이제 영구히 결정론적으로 처리됩니다. 모델이 매번 고민할 필요가 없어집니다. 코드를 하나씩 추가할수록 에이전트가 개입할 몫이 줄어듭니다 — 이게 핵심 메커니즘입니다.

    부수적으로: 변환기마다 약점이 다르니 반드시 두 가지 이상 포맷으로 시험해야 합니다.

2D 도면도 같은 파이프라인에 넣을 수 있나

됩니다. 다만 먼저 정직하게 짚을 것이 있습니다 — NVIDIA 스킬 중에 2D를 3D로 바꾸는 것은 없습니다. usd-convert-cad는 STEP·JT·DGN 같은 3D CAD만 다룹니다. 147개 스킬을 다 뒤져도 도면에서 입체를 만드는 것은 없습니다.

그래서 그 한 단계만 직접 만들었습니다. 나머지는 앞에서 검증한 파이프라인이 그대로 이어집니다.

명령 하나로 도면 → 시뮬레이션 가능 자산
$ ./scripts/run_pipeline.sh examples/drawing/bracket.dxf

되는 것과 안 되는 것 — 이게 제일 중요합니다 됩니다: 닫힌 윤곽 하나를 일정 두께로 밀어낸 부품 — 판재, 브래킷, 개스킷, 레이저·워터젯 절단물, 판금 전개도. 필렛·원호·슬롯·구멍 개수 제한 없습니다.

안 됩니다: 정면도·평면도·측면도 3개를 보고 입체를 복원하는 것. 이건 아직 연구 주제이지 옵션으로 해결되는 게 아닙니다. 회전체(선반 가공물)·스윕·로프트, 두께가 변하는 부품, 한 도면에 여러 부품이 있는 경우도 안 됩니다.

후자라면 이 도구는 맞지 않습니다. CAD에서 입체를 만든 뒤 usd-convert-cad로 가져오는 게 정직한 답입니다.

단위가 가장 흔한 사고 지점입니다

CAD 도면은 거의 항상 mm이고, USD 스테이지는 m입니다. 이걸 놓치면 1000배 큰 부품이 생기는데, 검증기는 전부 통과하고 물리만 이상하게 굽니다. 그래서 $INSUNITS에서 단위를 읽어 매번 출력하도록 했습니다. 단위 표기가 없는 도면이면 mm로 가정하고 경고를 띄웁니다.

질량도 형상에서 계산합니다 — 윤곽 면적에서 구멍을 빼고 두께를 곱한 부피에 밀도를 곱합니다. 예제 브래킷은 159.0 cm³ · 1.248 kg(강철)로, 손으로 계산한 값과 맞습니다. 질량이 맞아야 부품이 제대로 떨어집니다.

부딪힌 제약 두 가지

만들면서 발견한 것인데, 어디에도 잘 안 적혀 있습니다. 두 검증기가 서로 반대되는 파일 형식을 요구합니다.

검증기요구근거
simready-validate .usdc를 아예 무시 — 빈 리포트 {} api.py:396에 .usd/.usda만 허용
nvidia_usd_validate 대용량 배열이 든 .usda를 거부 UsdAsciiPerformanceChecker
해결: .usd — 확장자는 허용 목록에 있고, USD가 크레이트(바이너리)로 씁니다. 양쪽 다 통과합니다.

단일 부품은 표준 프로파일을 통과할 수 없습니다

모든 기본 Prop-* 프로파일이 FET004(다물체 물리)를 포함하고, 그 안의 RB.MB.001은 "강체가 최소 2개"를 요구합니다. 판재 한 장은 1개뿐이라 아무리 정확해도 통과가 불가능합니다.

NVIDIA도 이 기능을 "선택 사항"이라고 주석으로만 적어뒀습니다 — 기능 정의 JSON에는 optional 플래그 자체가 없어서 검증기는 다른 요구사항과 똑같이 강제합니다. 형식이 표현하지 못하는 의도는 도구가 지킬 수 없습니다.

해결 — 문서화된 확장 방식으로 profiles/prop-static.toml에 기본 프로파일에서 FET004만 뺀 Prop-Static-Neutral을 정의했습니다. --profiles-path는 반복 지정이 가능해서 기본 프로파일을 덮어쓰지 않고 추가됩니다. simready-foundation-add-profile 스킬이 존재하는 이유가 바로 이런 경우입니다. 관절이 있는 자산에는 기본 프로파일을 그대로 쓰세요.

도면 형식이 DXF가 아니라면

DXF가 기반이고, 나머지는 앞단에서 변환해 붙입니다(아래는 미구현 — 경로만 안내): DWG는 ODAFileConverter로, 벡터 PDF는 pdf2dxf나 Inkscape로, 스캔 이미지는 먼저 벡터화(potrace 등)해야 합니다. 다만 벡터화 결과는 윤곽이 닫혀 있지 않은 경우가 많아 손질이 필요합니다 — 이 컨버터는 닫힌 윤곽만 처리합니다.

05

먼저 알았으면 좋았을 함정 세 개

① 설치 순서만 틀려도 파이썬이 죽습니다

가장 당연해 보이는 설치 명령이 가장 확실하게 실패합니다. 이것 하나로 한 시간은 날립니다.

실제로 겪은 크래시
$ pip install usd-core usd-exchange urdf-usd-converter
Successfully installed usd-core-26.8 usd-exchange-2.3.0 ...

$ urdf_usd_converter arm2.urdf out/arm2
terminate called after throwing an instance of
'pxrInternal_v0_25_5__pxrReserved__::pxr_boost::python::error_already_set'
Aborted

# 버전을 맞춰봐도 소용 없음 — 크래시 종류만 바뀜
$ pip install "usd-core==25.5"
free(): invalid pointer

원인은 두 패키지가 각각 OpenUSD 전체를 자기 안에 품고 있고, C++ 네임스페이스가 같아서입니다. 같은 심볼이 두 벌 로드되면서 무너집니다. 게다가 site-packages/pxr 소유권까지 겹쳐서, 지우면 더 망가집니다.

해결 usd-core를 아예 설치하지 않습니다. usd-exchange가 이미 pxr을 제공합니다. 그리고 usd-core가 필요한 도구(simready-validate)는 별도 venv에 둡니다. venv 두 개는 우회가 아니라 설계입니다.

참고로 NVIDIA도 이걸 알고 있습니다 — 다만 그 경고가 site-packages/ovphysx/SKILLS.md 파일 안에만 적혀 있어서, 설치하고 나서야 볼 수 있습니다.

② 검증기의 자동 수정은 어디까지 해주나

일부러 망가뜨린 파일에 --fix를 걸어봤습니다. 결과가 흥미롭습니다.

nvidia_usd_validate --fix
$ nvidia_usd_validate broken.usda --fix
Subdivision scheme is not set ......... FixStatus.SUCCESS   (×2)
Prim does not have any extent value ... FixStatus.SUCCESS   (×2)
Stage does not specify an upAxis ...... FixStatus.NO_LOCATION
Invalid topology found ................ FixStatus.NO_SUGGESTION

재검사 → 6개 실패에서 2개로

6개 중 4개는 기계가 알아서 고칩니다. 남은 2개가 정확히 판단이 필요한 것들입니다 — NO_LOCATION은 “어느 레이어에 써야 할지 결정해야 함”, NO_SUGGESTION은 “진짜 데이터 오류”(없는 정점을 참조하고 있었습니다).

작업 분담이 여기서 나옵니다 SUCCESS가 나오는 것에 모델을 쓰면 토큰 낭비이고 위험만 늘어납니다. 에이전트는 NO_LOCATION과 NO_SUGGESTION에만 투입해야 합니다. 이 한 가지 원칙이 비용과 신뢰도를 동시에 좌우합니다.

③ Real2Sim 변환 결과가 자기네 검증기를 통과하지 못합니다

현실을 3D로 재구성한 결과(가우시안 스플랫)를 USD로 바꾸는 도구를 돌려봤습니다. 변환은 잘 되는데, NVIDIA 자체 검증기에서 2개 실패합니다.

실패해결결과
ByteAlignmentChecker .usdz 대신 .usdc로 저장 2 → 1
DefaultPrimChecker /World Xform으로 감싸기 1 → 0

두 번째는 형식 문제가 아닙니다. 기본 프림이 변환 불가능하면 그 재구성 결과를 씬에 배치·정렬·복제할 수 없습니다 — USD로 바꾸는 이유 자체가 사라집니다. Real2Sim을 쓸 거면 이 후처리를 재구성 직후에 반드시 넣어야 합니다.

07

Sim2Real과 Real2Sim

방향이 반대인 두 가지입니다. 헷갈리기 쉬우니 구분해두면 좋습니다.

Real2Sim — 현실을 시뮬레이션으로

카메라·라이다로 찍은 현실을 시뮬레이션 가능한 자산으로 바꿉니다. 단계는 이렇습니다.

  • GPU영상에서 카메라 위치 추정 — amc-* 스킬
  • GPU센서 기록을 NCore 형식으로 — ncore
  • GPU3D 가우시안 재구성 학습 — nre, VRAM 16 GB+
  • CPU재구성 결과를 USD로 — 여기만 검증했습니다
  • GPU시뮬레이터에 공급 — NuRec serve-grpc

캡처 장비가 없으면 physical-ai-datasets 스킬로 NVIDIA가 공개한 데이터셋을 쓸 수 있습니다(Hugging Face, 라이선스 동의 필요).

Sim2Real — 시뮬레이션에서 배운 것을 현실로

시뮬레이션에서 학습한 정책이 실제 로봇에서도 작동하게 만드는 일입니다. 간극이 두 종류입니다.

  • 시각합성 영상이 실제 카메라 영상과 다름 → Cosmos Transfer가 구조를 보존하며 사실적으로 변환
  • 물리시뮬 마찰·질량이 현실과 다름 → Isaac Lab의 도메인 랜덤화가 파라미터를 흔들어 과적합 방지
SimReady가 왜 이것의 앞단인가 PMT.001이 “모든 충돌 형상에 물리 재질을 연결하라”고 요구하는 이유가 여기 있습니다. 마찰·반발 계수가 바로 도메인 랜덤화가 흔드는 값입니다. 물리 재질이 안 붙은 자산은 흔들 대상이 없어서, 엔진 기본값에 과적합된 정책만 나옵니다. 규격 준수가 형식주의가 아니라는 뜻입니다.

참고할 만한 완성 예시

Isaac for Healthcare의 i4h-* 스킬 18개가 공개된 것 중 가장 완성된 폐루프입니다. 의료용이 아니어도 단계 쪼개는 방식은 그대로 참고할 만합니다: 씬 편집 → 사람 시연 수집 → 시연을 여러 궤적으로 증식 → 라벨링 → 학습 → 검증.

훔칠 만한 설계 결정 두 개. 첫째, 모든 단계를 따로 실행할 수 있게 만들면서 전체를 한 번에 돌리는 -e2e 스킬도 따로 둡니다. 둘째, smoke와 validate를 별도 스킬로 취급합니다 — 빠른 검사가 있어야 자동 루프를 안심하고 돌려둘 수 있습니다.

08

어떻게 시작하면 되나

전체를 관통하는 원칙 하나만 기억하시면 됩니다. 생성기보다 검사기를 먼저 설치하세요. 판정할 수 없으면 자동화는 그럴듯한 결과물만 만들어냅니다.

0단계 — 기준선 만들기 · 하루, GPU 불필요

저장소에서 바로
$ ./scripts/bootstrap_env.sh          # venv 2개 + 규격 파일, 약 3분
$ ./scripts/run_pipeline.sh examples/urdf/arm2.urdf

그리고 사용자님 자산 하나를 넣어보세요. URDF나 MuJoCo면 경로가 같습니다. CAD(STEP·JT 등)라면 usd-convert-cad가 필요한데, Kit 런타임과 별도 라이선스가 걸려 있어서 따로 계획하셔야 합니다.

통과 기준: 사용자님 자산 하나가 [PASSED]에 도달.

1단계 — CI 게이트로 걸기 · 2~3일, GPU 불필요

run_pipeline.sh는 회귀 시 종료코드 1을 반환하므로 그대로 쓸 수 있습니다. 두 가지만 챙기면 시간을 아낍니다. ~/.cache/warp/를 캐시하세요 — Warp가 첫 실행에 3.5초 컴파일합니다. venv 두 개도 캐시하세요.

통과 기준: 자산 품질을 떨어뜨리는 PR이 사람 검토 없이 자동 차단됨.

2단계 — 에이전트 투입 · 1주

스킬 설치
$ npx skills add nvidia/skills \
    --skill omniverse-cad-to-simready omniverse-usd-performance-tuning \
    --agent claude-code --yes

  omniverse-cad-to-simready   Safe   0 alerts
  ✓ installed → ./.claude/skills/...
Review skills before use; they run with full agent permissions.

그리고 에이전트에게 작업 분담을 명시하세요. 이게 가장 중요한 결정입니다.

신호담당
--fix → SUCCESS 도구. 모델을 부르지 말 것
NO_LOCATION에이전트 — 어느 레이어가 소유할지 판단
NO_SUGGESTION에이전트 — 실제 데이터 오류
이미 처리된 요구사항 코드스크립트. 그냥 실행
처리되지 않은 코드 에이전트 — 검사기 소스를 읽고 수정기를 확장

마지막 줄이 복리로 쌓이는 부분입니다. 규격이 실행 가능한 파이썬이니 에이전트가 검사기를 읽고 수정 코드를 추가할 수 있고, 그럴수록 결정론적으로 처리되는 비율이 올라갑니다. 단, 수정할 때마다 물리 검사를 반드시 함께 돌리세요 — 검사는 통과하는데 시뮬레이션이 깨지는 변경은 개선이 아니라 회귀입니다.

3단계 — GPU가 필요해지는 시점 · 2~4주

여기서야 GPU가 값을 합니다. 투자 대비 효과 순서는 ovrtx 렌더링 → Isaac Lab 강화학습 → NuRec Real2Sim → Cosmos·OSMO 워크플로입니다. MCP 서버도 이 단계에서 띄우세요 — 자산 처리가 아니라 Kit·Isaac 코드를 직접 쓰기 시작할 때 값을 합니다.

  • 핵심 요구사항 코드 → 수정기 등록표. 지금 6개를 처리합니다. 수십 개가 있습니다. 코드로 분기하는 표를 만들고 에이전트가 항목을 추가하게 하는 것이 가장 값나가는 자산입니다.

  • 안전 물리 보존 회귀 테스트. 지금은 “도는지”만 봅니다. 수정 전후 궤적을 비교하면 훨씬 강해집니다.
