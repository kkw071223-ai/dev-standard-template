01

읽는 법 — 층이 4개입니다

이름이 비슷해서 헷갈리는데, 실제로는 성격이 다른 네 층이 있습니다. 이걸 구분하면 나머지가 정리됩니다.

라이브러리
파이썬 패키지. 실제로 일을 합니다. pip install로 깔고 CLI나 파이썬으로 호출합니다. 에이전트 없이도 씁니다.
스킬
에이전트용 작업 절차서. 위 라이브러리들을 언제 어떤 순서로 부를지 적어둔 문서 + 실행 스크립트. 에이전트가 읽고 따라 합니다.
MCP 서버
질문 창구. “이 API 뭐야?”에 답합니다. 파일을 고치지 않습니다.
규격 (SimReady)
합격 기준. 위 셋이 만들어낸 결과물을 판정합니다. RB.006처럼 번호가 붙어 있어서 기계가 읽습니다.
각 항목 읽는 법 입력은 그 도구에 실제로 넘기는 것(파일 경로·옵션), 출력은 실제로 나오는 것(파일·JSON 필드·종료 코드)입니다. CPU는 GPU 없이 확인했다는 뜻, GPU는 GPU가 필요해 실행하지 못했다는 뜻, 키는 API 키가 필요하다는 뜻입니다.
02

라이브러리 13종 — 실제로 일하는 층

여기가 가장 중요합니다. 스킬은 결국 이것들을 부르는 절차서일 뿐이라, 이 층을 이해하면 스킬 없이도 파이프라인을 짤 수 있습니다. 아래 명령과 출력은 전부 직접 실행해서 얻은 것입니다.

변환기 — 다른 포맷을 USD로

urdf-usd-converter CPU실행함

로봇 기술 파일(URDF)을 USD로 변환. ROS 생태계의 로봇 정의를 Omniverse로 가져오는 표준 경로입니다.

입력
arm2.urdf (링크·관절·질량·충돌 정의) + 출력 폴더
출력
USD 자산 6개 레이어. 인터페이스 레이어 1개 + Payload/에 Contents·Geometry·Materials·MaterialsLibrary·Physics. 관절 한계가 라디안→도로 변환되고 NewtonJointAPI가 자동 부착되며, urdf:limit:effort 같은 원본 값은 custom 속성으로 보존됩니다.
$ urdf_usd_converter arm2.urdf out/arm2 # 2초 미만, 종료코드 0, 총 40 KB
mujoco-usd-converter CPU실행함

MuJoCo 모델(MJCF XML)을 USD로 변환. 강화학습 쪽에서 널리 쓰는 MuJoCo 씬을 가져옵니다.

입력
cartpole.xml (worldbody·joint·geom·actuator) + 출력 폴더
출력
USD 자산 4개 레이어(MaterialsLibrary 없음). 주의: 시각 재질을 만들지 않고, 하나의 프림이 시각·충돌을 겸합니다 — 이 때문에 SimReady VM.MAT.001에서 걸립니다.
$ mujoco_usd_converter cartpole.xml out/cartpole
usd-convert-gsplat CPU실행함

3D 가우시안 스플랫을 USD로 변환. 현실을 촬영해 재구성한 결과 (Real2Sim의 산출물)를 씬에 넣을 수 있는 형태로 바꿉니다.

입력
.ply 또는 .spz (속성 x y z · f_dc_0..2 · opacity · scale_0..2 · rot_0..3). 옵션: --up-axis Y|Z, --rotate-x/y/z, --generateSh, --generateScales
출력
ParticleField3DGaussianSplat 타입 프림 1개. 속성은 positions · opacities · orientations · scales · radiance:sphericalHarmonicsCoefficients. 주의: 기본 출력은 NVIDIA 검증기를 통과하지 못합니다 (정렬·기본 프림 문제, 후처리 필요).
$ usd-convert-gsplat -i scene.ply -o scene.usdc --up-axis Z [3DGS] Loaded 2,000 splats | SH degree: 0 coeffs # 112 KB → 307 KB
usd-convert-cad · usd-convert-asset PyPI 없음

CAD(STEP·JT·DGN·HOOPS)와 일반 3D 포맷을 USD로. 제조·설계 데이터를 가져오는 경로입니다.

입력
CAD 파일. 내부적으로 omni.kit.converter.jt_core 등을 씁니다.
출력
USD. 다만 PyPI에 없습니다 — Kit 런타임과 CAD Converter 라이선스가 필요합니다. usd-convert-asset은 스킬 문서가 “공개 패키지가 나올 때까지 비활성 경로”라고 명시합니다.

검증기 — 합격 여부를 판정

usd-validation-nvidia → CLI: nvidia_usd_validate CPU실행함

USD 파일이 문법·구조적으로 올바른지 검사하고, 가능하면 자동 수정. 에이전트 자동화에서 가장 많이 쓰게 될 도구입니다.

입력
USD 파일 또는 폴더. 주요 옵션: --fix(자동 수정) · --json-output · --csv-output · -c CATEGORY · -r RULE · --profile · --stamp
출력
이슈마다 프림 경로 + 요구사항 코드 + 수정 제안이 담긴 JSON. status는 PASS/FAIL, 각 이슈에 at.path, requirement.code(예 com.nvidia.usd.VG.010), suggestion.message. 종료 코드는 실패 시 1 — CI 게이트로 그대로 쓸 수 있습니다.
$ nvidia_usd_validate broken.usda --fix Subdivision scheme is not set ......... FixStatus.SUCCESS (×2) Prim does not have any extent value ... FixStatus.SUCCESS (×2) Stage does not specify an upAxis ...... FixStatus.NO_LOCATION ← 판단 필요 Invalid topology found ................ FixStatus.NO_SUGGESTION ← 판단 필요
simready-validate CPU실행함

자산이 SimReady 프로파일을 만족하는지 판정. “시뮬레이션에 쓸 수 있는가”를 기능(feature) 단위로 답합니다.

입력
USD 자산 + --profile(예 Prop-Robotics-Neutral) · --version · 규격 파일 경로 3개: --rules-path · --features-path · --profiles-path. 함정: --rules-path를 빠뜨리면 “프로파일을 찾을 수 없음”이라는 엉뚱한 오류가 납니다.
출력
기능 단위 JSON — features_summary에 각 FET___의 passed와 failing requirements(예 ['RB.006']). 콘솔에는 [PASSED]/[FAILED]. 실패 시 종료 코드 1.
$ simready-validate arm2.usda --profile Prop-Robotics-Neutral \ --rules-path $SPECS/capabilities --features-path $SPECS/features \ --profiles-path $SPECS/profiles/profiles.toml --output r.json [PASSED] Prop-Robotics-Neutral v1.0.0

작성·씬 — USD를 만들고 다루기

usd-exchange (usdex) CPU실행함

USD를 올바르게 만들어주는 SDK. 그리고 결정적으로 pxr(OpenUSD 파이썬)을 제공합니다 — 이 패키지 하나면 USD를 다 다룹니다.

입력
파이썬 API. usdex.core(스테이지·메시·머티리얼 작성), usdex.rtx(MDL 머티리얼)
출력
NVIDIA 규약을 지키는 USD 레이어. 절대 usd-core와 같이 설치하지 마세요 — 두 패키지가 각각 OpenUSD 전체를 품고 있어서 프로세스가 죽습니다.
ovstage CPU실행함

고성능 씬 데이터 계층. USD를 물리·렌더 엔진이 빠르게 읽을 수 있는 형태로 메모리에 올려두고, 질의·수정을 중계합니다. 엔진들 사이의 공용 버스입니다.

입력
ovstage.population.open_usd(stage, path, ordinal, domains=…). PopulationDomain으로 필요한 영역만 로드 (예 PHYSICS)
출력
질의 가능한 Stage 객체. Query·Filter·Hierarchy·PathDictionary로 프림을 찾고, dltensor_to_numpy로 데이터를 꺼냅니다.
ovstorage CPU임포트만

클라우드 자산 접근 API. S3·MinIO 같은 버킷이나 Nucleus 서버의 USD를 로컬 파일처럼 다룹니다.

입력
버킷·오브젝트 경로, 자격 증명
출력
자산 스트림·로컬 캐시. 주의 omniverse:// 주소를 쓰려면 libOpenGL.so.0이 있어야 합니다 (GPU와 무관, apt-get install libopengl0).

물리 — 실제로 움직이게

ovphysx CPU실행함

USD 기반 PhysX 물리 엔진. 자산을 실제로 시뮬레이션합니다. 강화학습용 환경 복제와 대량 데이터 입출력을 지원합니다.

입력
PhysX() 생성 → attach_ovstage(stage) → step_sync(dt). 데이터 교환은 create_tensor_binding(pattern=…, tensor_type=…) — 텐서 타입이 78종(관절 위치·속도·힘·질량행렬·자코비안 등)
출력
numpy(CPU)/DLPack(GPU) 텐서. 예: 관절 상태는 (환경수, DOF수), 링크 자세는 (환경수, 링크수, 7) = 위치3 + 쿼터니언4
$ python clone.py # 공식 샘플, GPU 없이 Created 3 clones successfully Rigid body binding: count=4, shape=(4, 7) env0: pos=(-0.0006, 0.2424, -0.0012) env1: pos=(0.0005, 0.6521, -0.0023)
한계
강체·관절·환경복제는 CPU에서 동작(GPU broadphase → ePABP 자동 전환). 변형체·입자는 CUDA 필수이며 조용히 건너뜁니다.
newton + warp-lang CPU실행함

Warp 위에 얹은 미분 가능 물리 엔진. Warp는 파이썬으로 GPU 커널을 작성하는 프레임워크이고, Newton은 그걸로 만든 물리 엔진입니다. 로봇 학습에서 물리를 미분해야 할 때 씁니다.

입력
@wp.kernel로 장식한 파이썬 함수 + wp.array(..., device="cpu"|"cuda"). 커널은 반드시 실제 파일에 있어야 합니다 — python -c로는 “exec()로 정의된 코드는 지원 안 함” 오류가 납니다.
출력
계산된 배열. 첫 실행에 JIT 컴파일 3.5초가 들고 ~/.cache/warp/에 캐시됩니다 — CI에서 반드시 캐시하세요.
$ python warp_cpu_test.py devices: ['cpu'] after 100 steps (1.0s): pos=[1.0, 0, 5.046] vel=[1.0, 0, -9.81] # 물리적으로 정확

렌더·스트리밍 — GPU 필요

ovrtx GPU임포트만

RTX 레이트레이싱 렌더링 + 센서 시뮬레이션. 합성 학습 데이터를 만드는 핵심입니다 — 카메라·라이다 이미지를 씬에서 뽑아냅니다.

입력
Renderer + RendererConfig, 렌더 대상 프림, RenderVarParam으로 원하는 출력 채널 지정
출력
RenderVarTensor — 색상뿐 아니라 깊이·법선·시맨틱 분할·모션벡터 같은 AOV를 텐서로 반환합니다. OVRTX_RENDER_VAR_PICK_HIT로 화면 클릭→프림 선택도 지원.
ovstream GPU 필수초기화 실패

화면 스트리밍 + 원격 입력. GStreamer 기반으로 렌더 결과를 클라이언트에 보내고 마우스·키보드를 되받습니다. 브라우저 뷰어의 전송 계층입니다.

입력
ServerConfig(width, height, target_fps, stream_port, …). 전송 5종 — WEBRTC · NATIVE · RTSP · SHM · CUDASHM
출력
영상 스트림 + 역방향 입력 이벤트 4종 (KEYBOARD · MOUSE · GAMEPAD · TOUCH). GPU 없으면 initialize()에서 libcuda.so.1 오류 — 제가 시험한 것 중 CPU 폴백이 없는 유일한 라이브러리입니다.
ovui PyPI 없음

파이썬 UI 라이브러리. 뷰어 창·패널·위젯을 만듭니다. ovrtx(그리기) + ovstream(보내기)와 한 조입니다.

입력
파이썬 UI 선언
출력
창·뷰포트. PyPI에 없어 소스에서 빌드해야 합니다.
03

MCP 서버 4종 — 도구 34개

전부 질문에 답하는 서버입니다. 파일을 만들거나 고치지 않습니다. 모델이 존재하지 않는 API 이름을 그럴듯하게 지어내는 걸 막는 용도입니다. 키 넷 다 NVIDIA_API_KEY가 필요해 실행하지 못했습니다 — 아래 도구 목록은 저장소 README에서 읽은 것입니다.

usd-code-mcp :9903 · 7개 API 키

OpenUSD API 사전. “이 클래스에 무슨 메서드가 있나”를 답합니다.

묻기
모듈·클래스·메서드 이름, 또는 자연어 설명
얻기
시그니처·문서·코드 예제. 도구: list_usd_modules · list_usd_classes · get_usd_module_detail · get_usd_class_detail · get_usd_method_detail · search_usd_code_examples · search_usd_knowledge
kit-mcp :9902 · 12개 API 키

Kit SDK 사전. Omniverse 앱을 직접 만들 때 씁니다. 익스텐션 400여 개와 설정 1000여 개는 손으로 찾기 어려운 규모입니다.

묻기
익스텐션 이름·기능 설명·설정 이름
얻기
익스텐션 상세·의존성 그래프·공개 API·설정값·앱 템플릿. 도구: get_kit_instructions · search_kit_app_templates · get_kit_app_template_details · search_kit_extensions · get_kit_extension_details · get_kit_extension_dependencies · get_kit_extension_apis · get_kit_api_details · search_kit_code_examples · search_kit_test_examples · search_kit_settings
omni-ui-mcp :9901 · 10개 API 키

omni.ui 사전. Omniverse 안에 패널·창을 만들 때.

묻기
위젯 이름, 레이아웃·스타일 방법
얻기
클래스 상세·스타일 문서·창 레이아웃 예제. 도구: get_ui_instructions · get_ui_class_instructions · get_ui_style_docs · list_ui_modules · list_ui_classes · get_ui_module_detail · get_ui_class_detail · get_ui_method_detail · search_ui_code_examples · search_ui_window_examples
isaacsim-mcp :9904 · 5개 API 키

Isaac Sim 사전. 로봇 시뮬레이션 앱을 만들 때.

묻기
Isaac Sim 익스텐션·설정·코드 패턴
얻기
도구: get_isaac_sim_instructions · search_isaac_sim_extensions · get_isaac_sim_extension_details · search_isaac_sim_code_examples · search_isaac_sim_settings
설치 docker compose -f docker-compose.ngc.yaml up 후 claude mcp add usd-code-mcp --scope user -t http http://localhost:9903/mcp. --scope user를 빼면 현재 폴더에서 실행할 때만 보입니다 — NVIDIA도 자기 README에서 이 함정을 경고합니다.
04

CAD → SimReady 스킬 (하위 15개)

omniverse-cad-to-simready는 라우터입니다. 직접 일하지 않고, 아래 15개 하위 레퍼런스를 순서대로 부릅니다. 실행 스크립트가 23개 들어 있습니다.

중요한 공통 규약 두 가지. 모든 하위 스킬이 scripts/check_dependencies.py --report dep.json으로 준비 상태를 먼저 점검하고, 실패하면 JSON에 해결 방법을 문장으로 돌려줍니다. 그리고 모두 --report(JSON)와 --markdown-report를 지원합니다.

preflight

파이프라인 전체의 사전 점검. 필요한 도구가 다 있는지 확인하고, 이후 단계들이 참조할 환경 변수 파일을 만듭니다.

입력
--env-file 저장 경로, --skip-content-agents(GPU 서비스 건너뛰기)
출력
PHYSICAL_AI_PREFLIGHT_MANIFEST 환경 파일 + 마크다운 리포트. 이후 스킬들이 이 매니페스트에서 도구 경로를 읽습니다.
identify-asset-context

자산이 무엇인지 파악. 파일 자체와 웹 검색으로 “이게 무슨 물건인지”를 알아냅니다 — 이후 재질·물리 배정의 근거가 됩니다.

입력
source_asset(필수) · output_directory(필수) · web_search(가능하면) · 선택: converted_usd_path · preview_image_path
출력
asset-context.json — 그 안의 recommended_web_queries가 다음 검색어 목록이 됩니다.
convert-to-usd · 변환 라우터

ovphysx 휠에 내장된 스킬 (6)

pip install ovphysx 하면 site-packages/ovphysx/skills/에 같이 들어옵니다. 경로는 ovphysx.ai_skills_path()로 얻습니다. 문서 136개와 CI 테스트된 예제 7개도 함께 옵니다 — 문서가 설치된 버전과 어긋날 수 없는 배포 방식입니다.

basic-workflow CPU실행함

최소 동작 예제. 생성 → 씬 붙이기 → 스텝 → 정리. 설치가 제대로 됐는지 확인하는 용도로도 씁니다.

입력
USD 씬 경로
출력
시뮬레이션 1스텝 성공. PhysX() → attach_ovstage() → step_sync() → release() 순서를 지켜야 합니다.
ovphysx-usd-authoring

물리 속성을 USD에 어떻게 쓸지. 강체·충돌체·질량·물리 씬을 .usda 텍스트나 파이썬으로 작성하는 방법.

입력
UsdPhysics.* API 또는 직접 작성. PhysX 전용 스키마는 ovphysx.codeless_schema_paths()로 등록
출력
ovphysx가 읽을 수 있는 물리 USD
clone-environments CPU실행함

강화학습용 환경 대량 복제. 씬 하나를 수천 개로 늘려 병렬 학습합니다. 이게 RL 처리량의 핵심입니다.

입력
복제할 프림 경로 + 복제 개수
출력
런타임 전용 환경들. CPU에서도 동작하지만 EnvIds 기반 필터링은 GPU가 필요합니다 (경고만 뜨고 진행됨).
tensor-bindings-cpu / -gpu CPU 확인

시뮬레이션 데이터 대량 입출력. 관절 위치·속도·목표값을 배열 단위로 읽고 씁니다 — 학습 루프의 병목이 되는 부분입니다.

입력
프림 패턴 + 텐서 타입(78종 중)
출력
CPU판은 numpy 배열, GPU판은 CUDA 포인터/DLPack — CPU 경유 없이 GPU↔GPU 교환이 가능해 PyTorch로 바로 넘길 수 있습니다.
ovphysx-output-read CPU실행함

결과를 ovstage 경로 그대로 읽고 되쓰기. 프림 경로 정보를 잃지 않아야 할 때 씁니다 — 텐서만 받으면 “몇 번째가 어느 프림인지”를 따로 관리해야 하는데 그걸 피합니다.

입력
ovstage 스테이지 + 읽을 출력 그룹
출력
ovstage에 되쓰인 결과(폐루프). 실행 결과: 프레임마다 11개 바디 속도 반전, 4개 출력 그룹 기록

i4h (18) · amc (3) — 폐루프의 실제 예시

i4h-*는 의료 로봇용이지만, Sim2Real 폐루프를 어떻게 단계로 쪼개는지 보여주는 공개된 예시 중 가장 완성도가 높습니다. 도메인이 달라도 구조는 그대로 베낄 만합니다. 전부 GPU 필요.

학습 데이터 만드는 사슬 — 이 순서가 핵심입니다

workflow-setup 환경 구축 → workflow-create 기존 환경을 포크해 새 과제 생성 → workflow-scene-edit 물체·카메라·성공 조건·랜덤화 편집 → dataset-teleop 사람이 직접 조종해 시연 기록(키보드·리더암·VR → HDF5) → dataset-mimic 시연 하나를 노이즈 주며 수천 개로 증식 → dataset-annotate VLM이 각 에피소드가 과제를 만족하는지 판정 → dataset-replay Isaac Sim에서 재생해 눈으로 확인 → dataset-convert HDF5 → LeRobot 포맷(parquet·비디오) → workflow-finetune GR00T·openpi PI0 정책 학습 → workflow-validate 정책 롤아웃 평가 → workflow-e2e 위 전부를 한 번에

여기서 배울 점 두 가지 첫째, 모든 단계를 따로 실행할 수 있으면서 -e2e도 따로 있습니다. 한 단계만 디버깅할 수도, 전체를 돌릴 수도 있습니다. 둘째, smoke와 validate가 독립 스킬입니다. 빠른 검사가 있어야 자동 루프를 안심하고 켜둘 수 있습니다.

특히 mimic(시연 1개 → 수천 개)이 이 구조의 핵심입니다. 사람의 시연은 비싸고 시뮬레이션 증식은 쌉니다.

Real2Sim 분기 — 디지털 트윈 (6)

catheter-navigation-setup 요구사항 확인 · -digital-twin 실제 CT 영상 → 환자 혈관 디지털 트윈 · -render-drr 시뮬레이션에서 실제 X선 같은 이미지 생성 · -viewport 대화형 뷰포트 · -smoke CPU 전용 빠른 검사 · -e2e 전체 · lerobot-viz 궤적 시각화

-render-drr이 흥미롭습니다 — 시뮬레이션 결과를 실제 장비 영상처럼 만들어 시각 간극을 줄이는 접근입니다. Cosmos Transfer와 같은 문제를 도메인 특화 방식으로 풉니다.

amc — 카메라 캘리브레이션 (3)

amc-setup-calibration-stack Docker로 서비스 기동(NGC 키 필요) · amc-run-sample-calibration 번들 샘플로 설치 확인 · amc-run-video-calibration 내 MP4로 캘리브레이션(REST API)

입력 여러 대 카메라의 영상 또는 RTSP 스트림 → 출력 카메라 외부 파라미터(위치·자세). 고정 카메라 환경을 Real2Sim으로 옮길 때의 첫 단계입니다 — 카메라가 어디 있는지 모르면 재구성이 시작되지 않습니다.
