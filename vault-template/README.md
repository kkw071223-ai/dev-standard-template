Phase 3에서 `C:\agent\vault`로 복사한다. 설계서 §6.5 / §9 / §18의 구조를 파일로
옮긴 것이다.

```
00-inbox/          분류 전. 매일 비운다
10-domains/        도메인별 상설 지식 + flows/
20-facts/          검증된 사실 카드. 추가만, 수정 금지
30-runs/           런 리포트. 불변, 누적. 그림·영상 포함
40-refs/           외부 문서 요약. URL + 조회일 필수
50-daily/          일일 노트
90-meta/
  templates/       FLOW.md · RUN.md · FACT.md
  archive/         구축 문서가 세팅 완료 후 들어오는 곳
  architecture.md  구성도. 구조가 바뀔 때만
  ENVIRONMENT.md   자동 생성. 주 1회 Conductor가 덮어쓴다
```

## 세 가지 문서, 세 가지 수명

| | 언제 만드나 | 언제 고치나 | 언제 버리나 |
|---|---|---|---|
| **FACT** | 명령으로 확인한 직후 | **절대 안 고침** | `expires` 도달 시 재검증 또는 강등 |
| **FLOW** | 플로우가 **두 번째로 성공**했을 때 | 실패를 진단할 때마다 5절에 한 줄 | `deprecated` 표시. 삭제하지 않음 |
| **RUN** | Conductor가 자동 | **절대 안 고침** | PNG 영구 / MP4 90일 |

## 왜 이렇게 나누나

런은 사건이고, 플로우는 그 사건들에서 배운 것이고, 사실은 확인된 것이다.
셋을 한 파일에 섞으면 무엇이 검증됐고 무엇이 추측인지 구분이 사라지고,
그 순간 환각을 막을 방법이 없어진다.

**RUN → FLOW 5절이 유일한 학습 고리다.** 진단한 실패가 플로우 문서로 올라가지
않으면, 이 시스템은 매번 같은 실수를 반복하는 자동화일 뿐이다.
